# OpenCode 配套升级迁移

本地源码版本 `0.1.0-dev.7`。迁移只处理指定旧检查点的隔离副本，发布包含新领域状态与新引擎快照的子代次。原宿主、旧引擎程序和原检查点保留。安装和迁移是明确的维护操作，不是后台自动更新。

## 为什么不能只替换 exe

引擎可以在启动时修改自己的数据库。旧会话“还能读”不足以证明工具结果、附件字段和后续权限行为没有变化；旧程序也不保证能读取新引擎改过的数据。因此普通恢复仍严格要求引擎版本匹配，现有宿主启动增加版本及二进制 SHA-256 绑定。离线查看不会启动引擎，离线模型设置也不能绕过这个约束。模型重新配置及失败后的重启复用相同绑定检查。

## 迁移过程

1. 保存并退出星杳；迁移取得宿主写锁，只接受便携库唯一完整分支的最新代次。宿主身份、schema、修订和保存代次必须与它一致。仍在执行或结果待核实的任务会阻止迁移。
2. 读取旧/新发行清单与真实验收报告。目标报告必须包含这两个准确引擎制品的升级测试证据；再核对实际 exe 哈希与 `--version`。
3. 在宿主下创建 `.engine-migration-*`。旧领域库及 WAL 辅助文件只复制到此处检查；不会用 SQLite 打开原宿主来检查，从而避免“只读”仍创建辅助文件。
4. 把旧检查点的领域库和引擎库恢复到隔离目录，用旧引擎通过公开 API 逐个读取产品任务绑定会话，记录完整公开 JSON 的摘要。随后停止旧引擎，以新引擎打开同一副本，由 OpenCode 执行其自身迁移，再核对摘要。
5. 迁移不加载模型配置，不发送模型请求。公开消息包含附件与工具扩展字段，摘要递归排序对象键、保留数组顺序；正文不写入迁移凭据。会话读取前后还会核对元数据，任何差异或未处理权限都拒绝发布。
6. 新旧 exe 再次核对后，更新副本的版本绑定并创建配套检查点。证据位于 `upgrade/engine-migration.json`，纳入检查点哈希清单。发布时再次核对父代次；不能在并发新分支后强行追加。
7. 安装同一受测发行后启动，原本干净的旧宿主通过已有配套恢复流程接续新代次。旧代码恢复应使用原检查点与隔离宿主/便携库，不能打开新数据库充当回滚。

## 维护入口

在产品源码目录中使用 Bun，所有路径均为绝对路径。`from-release`、`to-release` 使用带 `release-validation.json` 的候选目录；已安装制品的报告可能存于选择日志，不能假定旁边有同名文件。原项目应使用创建会话时的稳定路径。

```powershell
bun run script/migrate-engine.ts --help
# 按输出传入 --from-release、--to-release、--host-root、--vault-root、--generation、--project。
```

成功会返回新代次、父代次、身份、隔离路径和迁移凭据。它不修改当前发行选择。失败会保留隔离副本，并给出路径。若在完整代次发布后退出或报错，先核对最新检查点的迁移凭据，再安装对应发行继续；再次指定旧父代次会被拒绝，不会生成第二个分支。当前没有一键升级界面或自动迁移重试。

## 验证范围与未覆盖项

`test/engine-upgrade.test.ts` 用真实 engine.5 与 engine.6-source、临时身份、纯本机模型夹具，检查完整历史、非零 shell 结果、拒绝读取、迁移前故障、原件保全、产品任务续接、新版配套恢复和旧版独立恢复。`test/engine-binding.test.ts` 检查同宿主版本/hash、不明来源库、离线设置绕过和服务版本不符；`test/migration-qualification.test.ts` 检查发行证据是否绑定准确制品。实际验收结果单独写入发行记录，不由本文声明通过。

当前摘要范围是**所有产品任务已绑定的会话**。不能把 legacy `/session` 一次返回的默认 100 条记录当作全量；未绑定会话、未登记的子会话和外部附件文件不在逐项语义验收内。完整引擎数据库仍配套备份，但不能由此推断这些范围都已逐项验证。当前没有手工更改 OpenCode 私有表。

故障注入抛错证明常见阶段失败的保全与停止逻辑；不等于真实断电、磁盘损坏或恶意本地进程竞速的证明。迁移暂存副本暂不自动清理，容量策略仍待完成。历史 engine.5 的原构建输入不完整，只固定与测试现存准确二进制；不声称可以逐字节重建。
