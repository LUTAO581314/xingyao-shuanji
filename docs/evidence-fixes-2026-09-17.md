此次脚本中的 8 组断言全部通过。它们覆盖结果分类、结构化证据、非成功来源的学习门槛、承诺默认固定、固定约束溢出、修订去重、事件年龄与旧记忆迁移，以及历史基线未被覆盖。更广的来源修订、隐私删除、封存和旧动作迁移回归位于 `test/source-revisions.test.ts`；其验收结果应以实际测试命令输出为准。

迁移采用持久标记：`source_revision_version=1` 负责动作修订根与记忆时间补齐，`action_evidence_version=1` 负责旧动作结构化结果可信度重核，`action_evidence_validation_version=1` 重核已有结构化证据的形状与一致性，`root_learning_policy_version=1` 统一同根封存策略。旧库缺 marker 时在打开事务中补齐，原始正文不被升级过程删除。当前字段 `sourceObservedAt` 与归档时间 `createdAt` 分开保存；新纠正来源拥有自己的新事件日期。已经带完成 marker 的库不会因为再次打开而重新执行迁移。

领域写入也校验执行证据的版本、枚举、时间、退出码和内部一致性；存在有效证据时从证据派生动作状态，避免内部调用写入“退出码失败但状态成功”。历史矛盾记录降为未知、撤回派生结论，只有新的有效对账才能重新建立证据。同一执行根的封存策略取保守交集：任一已接受修订在封存期间进入，后续仅更新内容不能恢复该执行根的情绪或学习权限。封存期间进入的非终态结果在解封后完成，也不补记该根；解封后新的独立调用可正常学习。

领域数据库格式升为 schema 2。旧 schema 1 库在打开前先与检查点比较：干净的旧宿主先恢复已知最新代次，随后迁移；真正的未同步分支在修改前被拒绝。迁移增加修订号，直到新的完整检查点保存后才显示已同步。历史 schema 1 检查点按原始字节验证和恢复，禁止父代 schema 2 追加 schema 1 子代。普通升级不能降低数据格式，回滚必须使发行与配套检查点一致。相关回归位于 `test/startup-migration.test.ts`、`test/checkpoint.test.ts`、`test/releases.test.ts` 与 `test/launcher.test.ts`。

独立复查用真实 `.4` 二进制重现了旧程序忽略 schema 2 检查点、在同库写出第二个 schema 1 分支的情况。因此新的发行选择和启动入口会检查整个便携库：存在高于目标程序 schema 的完整检查点时，拒绝启动旧程序，并要求隔离便携库与宿主恢复副本。仅恢复一个匹配的旧库不再足够。新版仍能验证、恢复并迁移 schema 1 检查点；自动创建隔离回滚库尚未实现。此保护约束新的选择/启动入口，无法改变直接手工执行旧二进制的行为。

对于未来未知 schema 或更高完成清单格式，发现可识别的完成记录时也会明确拒绝使用整个库；不能把“不支持”当作“没有这份历史”而继续追加。中断写入和损坏记录仍不算可恢复候选。恢复分支保存新检查点并继续产生未同步工作后，启动会验证当前代次到原配对恢复根的父链；真实子进程崩溃重启回归确认同一分支工作保留，不重新覆盖为旧根。

另以真实 OpenCode engine.5 配合本地确定性模型服务执行了 shell 回归：`exit 7` 记录失败和退出码 7；超时记录未知和 null；`exit 0` 记录工具成功；权限拒绝记录失败。任务仍等待用户验收。此回归位于 `test/real-engine.test.ts`，验证实际执行协议，并不验证公网模型的生成质量。`test/tool-evidence-api.test.ts` 另外覆盖上游 HTTP 数据、结构化结果、重复修订、旧证据撤回与旧库迁移的完整领域链路。

本次脚本另外重现了一个仍然存在的学习限制：在选定来源以外加入十条新失败动作，不会自动改变该候选的样本集合，因为系统尚未记录“这些动作是否实际采用该技能”。报告将数值明确标为所选调用的统计值，不能理解成技能能力或成功率的验证。

记忆遗忘仍主要体现为检索排序中的新鲜度衰减。当前修复没有加入语义压缩、自动删除、人物关系建模或长期人格成长。同样，shell 的工具结果与用户任务是否完成是不同层次的验证；一条命令退出成功不能证明用户目标已经达成。

revision 本身是不透明字符串。已见旧版本、终态之后迟到的非终态快照，以及结束时间明确更早的结果会被阻止回退；对于两个首次见到、又没有可排序时间的终态版本，系统仍不能仅靠哈希确定先后。这是需要在上游协议和后续兼容性验证中继续约束的边界。
