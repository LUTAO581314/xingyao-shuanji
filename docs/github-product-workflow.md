# 用 GitHub 承载星杳的持续开发

核查日期：2026-09-18。对象为 `LUTAO581314/xingyao-shuanji`，公开仓库。以下区分已核实状态与建议，不表示已经配置 Actions、发布源码分支或自动升级。

## 当前状态与最先解决的问题

GitHub API 核实默认分支为 `conversation-archive`；当前远端分支列表只有该分支。聊天档案会按导出截止时间更新，具体提交以远端和档案 manifest 为准。本地产品源码位于 `F:/codex/xingyao` 的 `product-v2`，并指向同一个 origin，但尚未作为产品分支发布。聊天导出工具和可见对话档案已经在远端。

因此仓库目前帮助保存设计讨论，尚未形成“从源码构建产品、验证升级、下载合格发行”的协作入口。产品数据库、模型凭据、用户文件与媒体属于运行资料；GitHub 的职责是保存代码、设计决定、补丁、测试和可分发制品。对话档案是独立的时间点记录，恢复完整身份需要产品的配套检查点和资产副本。

## 建议的仓库结构

```text
main                         产品源码主线，逐步取代聊天分支作为默认入口
  src/                       运行时、公开接口适配器、工作台
  test/                      领域、恢复、真实引擎及编译产品回归
  patches/opencode/          上游基线、必要补丁、哈希与退出条件
  script/                    构建、验收、安装及迁移验证
  docs/                      架构、实际能力、已知限制、发行证据
  evals/                     后续中文长期记忆任务和评分依据
  .github/workflows/         Windows 候选构建与完整验收（本地已编写）
conversation-archive         已有可导出聊天档案，独立保留
feature/*、fix/*              有范围的修改，通过 PR 进入主线
```

当前源码本身适合一个产品仓库。无需为了文件、图谱、睡眠和人格各建一套独立仓库。完整 OpenCode 修改若需长期维护，可单独维护一个引擎 fork，并由产品 manifest 固定源码提交、构建方式、版本和 SHA-256；本产品仍通过 `adapter.ts` 对接公开接口。

## GitHub 功能与实际用途

| GitHub 能力 | 用于本产品 | 合格条件 |
|---|---|---|
| Git / PR | 代码、数据结构变更、必要引擎补丁的审阅历史 | 每项变更解释触发条件、行为变化、验证与迁移影响 |
| Issues / Milestones | 把架构缺口拆成可验收任务 | 用可复现输入和通过标准描述，避免只写“更聪明” |
| Actions | Windows 类型检查、结果链测试、恢复测试、候选构建 | 真实引擎和编译产品测试必须执行，跳过不能等同发行通过 |
| Releases | 携带引擎的便携包、哈希、变更说明、兼容表 | 制品绑定源码和真实通过报告，保留上一合格版本 |
| 上游候选 PR | 评估 OpenCode 新提交、修复补丁冲突、继续旧会话 | 在隔离副本验证数据迁移与恢复；通过后才成为可选更新 |
| conversation-archive | 按用户要求保留主任务与子智能体的可导出记录 | 脱敏、来源范围、截止时间与文件哈希明确 |

## 自动化前需要补齐的工程条件

1. **完整引擎构建来源已补齐。** 四份补丁从公开提交 `e03db9bc6908f75c9334d8aa997deeaac81c0298` 重放为固定 tree；原记录中的 `d0a9…` 是本地产物，不能用于公共 CI 下载。源码准备、锁定依赖、固定模型快照、编译与工具版本记录已由本地独立目录执行成功；详情见 [引擎来源](engine-source.md)。历史 engine.5 缺少原模型快照，仍不宣称可逐字节重建。
2. **开发机路径依赖已从构建入口移除。** 许可证由参数或引擎旁文件提供，缺少即失败；产品包携带完整补丁队列，并校验传入的引擎构建记录。浏览器使用 Edge channel 或显式浏览器路径，记录实际浏览器版本；截图进入 reports。CI 固定 Bun 1.4.2、Node 26.8.1、Python 3.12.14；VS/MSVC 与浏览器的实际版本写入证据，Windows runner 镜像仍可能变动。
3. **分开普通检查与发行门禁。** 普通 PR 可先做类型和领域测试；Windows 候选任务负责实际引擎、配套恢复、独立编译入口和浏览器测试。发行门禁沿用 `script/verify-release.ts` 的零失败、零跳过、制品哈希匹配要求。
4. **补项目发布说明。** 根 README 应先介绍实际可用版本和启动方式，随后说明未完成能力；项目许可证与第三方许可一起维护。大型可执行文件放 Release assets；凭据、活动数据库、便携快照和媒体资料采用各自存储流程。
5. **升级只生成候选。** 上游更新可以触发检查，但不能仅因补丁能套用、HTTP health 正常就切换用户引擎。合格升级需要旧会话续接、失败/超时结果、数据迁移、崩溃恢复、旧版本配套恢复的实际证据。

## 开源组件如何进入这个流程

| 组件 | 保持的职责 | 集成记录 |
|---|---|---|
| OpenCode | 模型会话与工具执行引擎 | 固定源码/制品、最小必要补丁、公开接口与迁移回归 |
| Cytoscape.js | 文件、知识和记忆关系的浏览 | 本地打包固定版本；关系事实、修订和删除仍由领域库管理 |
| Infinite Canvas | 图片、视频及视觉方案编排 | 单独模块；先落实媒体资产、任务/取消、凭据接口和便携保存 |
| Graphiti / LightRAG | 候选记忆抽取或资料检索增强试验 | 先在隔离中文评估集比较收益，再决定是否增加服务依赖 |

所有组件进入仓库前都应记录上游地址、固定版本/提交、许可证、使用的接口、数据持久化方式与替换条件。详细选型依据见 [工作台模块与开源选型](workbench-modules.md)。

## 接下来的顺序

本地已写入 `.github/workflows/windows-candidate.yml`：对 main/product-v2 的推送与 PR 执行准备源码、引擎编译、产品编译和 `verify-release.ts`；只有通过完整门禁才保存候选。Action 按提交 SHA 固定，contents 权限为只读，无上传 Release、推送代码或切换用户引擎步骤。聊天分支不触发引擎构建。**尚未在 GitHub hosted runner 执行，不能把本地结果当成远端绿灯。**

下一步将可审阅源码作为产品分支发布，完成首次 hosted runner 验证，再考虑把 main 设为默认入口、开启必需状态检查。engine.5→engine.6 的配套迁移入口和专门回归已加入本地源码，具体通过范围见 [升级迁移](engine-upgrade.md)。本地合格与远端合格分别记录。

**首次 CI 还有一个明确的输入条件：历史 engine.5 制品尚未作为 Release asset 发布。** workflow 在引擎编译前读取仓库变量 `XINGYAO_UPGRADE_BASELINE_TAG`，从本仓库指定 Release 下载 `opencode.exe`，并以源码中固定的 SHA-256 `528277b2ea4178093a192da0fe33ef4768e7ae5514a7b21de006d07212c6df83` 核对。没有变量、资产或准确字节都会直接失败，不能用重编译的近似版本替代，也不能跳过升级回归。历史基准 Release 应标清“测试基准，不是推荐下载版本”，附上许可证和来源限制；代码仓库不存这个大二进制。这里仅配置消费路径，没有创建 Release 或仓库变量。

每次候选构建的目标引擎哈希可能不同。因此发行门禁将当前候选 manifest 的准确哈希传给迁移测试，并在 `release-validation.json.engineUpgrade` 记录实际受测的源/目标版本与哈希。它不复用另一台构建机的通过结论。旧基准始终固定。

本地同时准备了问题模板、能力验收模板与 PR 描述模板。模板让每项任务包含触发条件、验证方式和恢复影响；不会自动创建公开 Issue 或向他人发送消息。
